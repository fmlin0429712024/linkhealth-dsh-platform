# Synthetic ICHD Documentation Audit Rules

> These rules are fictional examples for workflow demonstration. They are not clinical, coding, billing, quality, or compliance guidance.

| Rule ID | Method | Domain | Synthetic trigger | Required evidence to draft a finding | Agent output | Human decision |
| --- | --- | --- | --- | --- | --- | --- |
| SYN-ICHD-01 | deterministic | treatment | A `clinical_treatments[]` item completed materially earlier than scheduled (`scheduled_minutes − completed_minutes ≥ 15`) | Treatment duration | Run via `deterministic-rule-audit` skill (batch) or `tools/query_deterministic_rule.py` directly (single check); either way, report the SQLite-backed result verbatim | Confirm, reject, or request clarification |
| SYN-ICHD-02 | non-deterministic | treatment | `treatment_note` documents a patient refusing or discontinuing treatment early | `treatment_note`, `follow_up_note`, and the narrative use-case description in the `treatment-refusal-review` skill | Apply the skill's use-case description; cite which of the four judgment points are documented vs. an evidence gap | Confirm adequate, request clarification, or flag the gap |
| SYN-ICHD-03 | non-deterministic | treatment | `follow_up_note` is present | Follow-up statement when documented | Flag an evidence gap only | Decide whether action is needed |
| SYN-ICHD-04 | non-deterministic | treatment | `treatment_note` documents a symptomatic blood-pressure drop (hypotension event) | `treatment_note`, `follow_up_note`, and the narrative use-case description in the `intradialytic-hypotension-review` skill | Apply the skill's use-case description; cite which of the four judgment points are documented vs. an evidence gap | Confirm adequate, request clarification, or flag the gap |
| SYN-ICHD-05 | non-deterministic | patient | A `patient.nursing_notes` entry documents a care-plan-relevant change (e.g. a medication adjustment) — requires `data/synthetic-ichd-patient-goldset-multi-domain.json`; the original gold set has no `nursing_notes` field | The triggering `nursing_notes` entry, the next relevant `clinical_treatments[]` entry's `treatment_note`/`follow_up_note`, and the narrative use-case description in the `patient-continuity-review` skill | Apply the skill's use-case description; cite which of the four judgment points are documented vs. an evidence gap | Confirm adequate, request clarification, or flag the gap |
| SYN-ICHD-06 | deterministic | patient | Fewer than 3 entries in `patient.nursing_notes` (`nursing_notes_count < 3`) — requires `data/synthetic-ichd-patient-goldset-multi-domain.json`; resolved via a **separate** SOP store, `data/audit_rules-multi-domain.db` (never added to the shared `data/audit_rules.db`, to avoid changing what Phase 1/2 evaluate) | Count of `patient.nursing_notes` entries | Run `tools/query_deterministic_rule.py SYN-ICHD-06 - --db data/audit_rules-multi-domain.db` (single patient-level check, not looped per treatment); report the SQLite-backed result verbatim | Confirm, reject, or request clarification |
| SYN-ICHD-09 | deterministic | treatment | A `clinical_treatments[]` item has `status == "missed"` | `status` | Run via `deterministic-rule-audit` skill (batch) or `tools/query_deterministic_rule.py` directly (single check); either way, report the SQLite-backed result verbatim | Confirm, reject, or request clarification |

**Method** distinguishes how the trigger is decided: `deterministic` rules are resolved by `tools/query_deterministic_rule.py` against a SQLite SOP store — the agent invokes the tool and reports its result, it does not judge the threshold itself. Treatment-domain deterministic rules (`SYN-ICHD-01`/`09`) use the shared `data/audit_rules.db`; the patient-domain deterministic rule (`SYN-ICHD-06`) uses a separate store, `data/audit_rules-multi-domain.db` (see that row above and `--db` in `tools/query_deterministic_rule.py`). `non-deterministic` rules require reading free-text notes and applying judgment against a described scenario; there is no formula, only a narrative use-case description (in the relevant skill) that the LLM reasons against.

**Domain** distinguishes which record scope the rule evaluates: `treatment` rules evaluate a single `clinical_treatments[]` entry in isolation. `patient` rules evaluate `patient`-level fields that span the whole record — `SYN-ICHD-05` (non-deterministic; also cross-references one treatment record to judge continuity — see `patient-continuity-review`) and `SYN-ICHD-06` (deterministic; a single count-based check, see `deterministic-rule-audit`). This column exists to keep the treatment-domain and patient-domain skill sets legible as two distinct, independently extensible groups — see `docs/prd-multi-agent-domain-split.md`.

## Guardrails

- Cite only source fields available in the synthetic gold set.
- Never infer a diagnosis, code, causality, or reimbursement impact.
- State `insufficient evidence` when documentation does not support a conclusion.
- Route every finding to a qualified human reviewer.
